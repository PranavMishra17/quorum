# R10 — Observability and tracing for an agent turn

**Band:** B · **Closes:** no numbered `D-0xx` (none in `docs/DECISIONS.md` names R10 explicitly) — substantiates the `agent_events`/`llm_calls` schema in `docs/ARCHITECTURE.md` §2–3 and unblocks the internal view (README, "The agent internal view *(planned)*"). Recommends opening a new decision, **D-019 — event/trace ID hierarchy**, to track the choice made here.

## Question

`agent_events` is described in the README as "the best thing in the project," but as scaffolded it is a flat, timestamped log: `id, chat_id, turn_id, message_id nullable, event_type, payload jsonb, created_at`. A log answers "what happened." A trace answers "what happened, in what order, inside what, and how long did each part take" — which is what the internal view actually needs to show a non-engineer reviewer *why* the agent did or didn't respond, and where a turn's latency and cost went. The question is whether `agent_events` can become a real trace cheaply, without adopting an OpenTelemetry SDK dependency, and what schema and ID discipline that requires.

## Findings

**1. Correlation ID hierarchy.** OpenTelemetry's own model is the right reference even without the dependency: a trace has one `trace_id` (128-bit) shared by every span in it, and each span has its own `span_id` (64-bit) plus a `parent_span_id` pointing at the span that created it — a valid trace/span ID is any non-zero byte array of that length ([OTel trace API spec](https://github.com/open-telemetry/opentelemetry-specification/blob/main/specification/trace/api.md)). Mapped onto Quorum:

- `turn_id` = the trace id. One row per agent turn in a new `turns` concept (or simply the UUID already threaded through `agent_events` and `llm_calls` per `docs/ARCHITECTURE.md` line 83) — everything belonging to one turn shares this.
- `request_id` = the id of the inbound HTTP request that started the turn (one per `api/agent/turn/route.ts` invocation). Distinct from `turn_id` because a retried/duplicate request (see D-011, idempotency) can map to the *same* `turn_id` without being the same request — this is exactly the seam R8/D-011 needs.
- `llm_call_id` = the primary key of the `llm_calls` row for one model call within the turn — the "chat span" in OTel terms.
- `tool_call_id` = one per tool invocation inside the tool loop — the "execute_tool span" in OTel terms.
- Every one of these carries `turn_id` as a foreign key, and `llm_call_id`/`tool_call_id` rows optionally carry a `parent_event_id` or `caused_by_llm_call_id` when a tool call was itself dispatched from a specific model response (parallel tool use, see R11).

This gives `turn_id` → `agent_events.turn_id` / `llm_calls.turn_id` as the trace, and `id` (event) / `id` (llm_calls row) / a new `tool_calls` identifier as the spans, with parent linkage recorded as a field rather than inferred from ordering.

**2. What OTel's span concepts suggest, without the dependency.** OTel distinguishes three annotation mechanisms on a span ([OTel traces concepts](https://opentelemetry.io/docs/concepts/signals/traces/)):
- **Attributes** — static key/value metadata with no independent timestamp (e.g. `gen_ai.request.model`).
- **Events** — timestamped points *within* a span's duration (e.g. "first token received").
- **Links** — causal references to spans in *other* traces (used for async fan-out).

`agent_events.payload` (jsonb) already plays the attributes role. What it does not yet do is distinguish a *span* (has a start and end, a duration) from a *point event* (instantaneous). Recommendation: keep `agent_events` as the point-event log it already is (`gate_evaluated`, `memory_retrieved`, `tool_invoked`, `tool_result`, `context_dropped`), and treat `llm_calls` as the one first-class **span** table, since it already has the fields a span needs (start-implied by `created_at`, `latency_ms` as duration, `model`/`purpose` as attributes). A `tool_calls` table (new, or a payload-typed pair of `agent_events` rows for `tool_invoked`→`tool_result` with a shared `tool_call_id`) plays the same role for tool spans. This avoids inventing a generic "spans" table — `agent_events` stays append-only and cheap, and the two things that actually have meaningful duration (`llm_calls`, tool calls) get first-class start/end timestamps.

The official GenAI semantic conventions (moved out of the general `semantic-conventions` repo into a dedicated GenAI repo — the `main` docs link 404s as of this research, confirming the migration; content recovered via the OpenTelemetry blog and the still-live `opentelemetry.io/docs/specs/semconv/gen-ai/*` pages) describe exactly this three-tier hierarchy for agent systems: a top-level `invoke_agent` span, child `chat` spans per LLM call, and leaf `execute_tool` spans per tool call, with span name `{gen_ai.operation.name} {gen_ai.request.model}` and span kind `CLIENT` ([OpenTelemetry GenAI observability blog, 2026](https://opentelemetry.io/blog/2026/genai-observability/); [OTel GenAI attribute registry](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/)). Mapping: `invoke_agent` ≈ the turn (`turn_id`), `chat` ≈ an `llm_calls` row, `execute_tool` ≈ a tool-call pair of events. Key attribute names worth adopting verbatim in `llm_calls`/payloads for familiarity to anyone who has used an OTel-instrumented LLM stack: `gen_ai.request.model`, `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.response.finish_reasons`. Quorum's existing `llm_calls` columns (`model`, `input_tokens`, `output_tokens`) already line up; no rename is required, but documenting the OTel-equivalent name in a code comment costs nothing and helps portability if OTel export is ever added.

**Uncertain:** the canonical `gen-ai-spans.md` document itself returned a "moved" redirect from both the old and a guessed new path during this research; the content above is reconstructed from the OpenTelemetry blog post and the still-resolving attribute-registry page, not read verbatim from the spec document. If a future contributor wants the authoritative attribute table, they should locate the current `semantic-conventions-genai` (or successor) repository at time of reading — the exact URL was not confirmed live.

**3. Latency attribution.** Per `docs/ARCHITECTURE.md` §3, a turn passes through: idempotency check → persist message → build `ScopedAgentContext` → rate limit → gate → retrieve memory → assemble context → model call → tool loop → persist → (deferred) extract. Each of these has a plausible duration. The cheapest correct approach, consistent with "filter before rank" and "one append-only writer" (`lib/events/log.ts`): every step that isn't already an `llm_calls` row writes a `agent_events` row with `event_type` ending in `_started`/`_completed` (or a single event with `duration_ms` in its payload, computed by the caller). Given `agent_events` is insert-only, the cheaper option is one event per step with a `duration_ms` field in `payload` rather than paired start/end rows requiring a join to compute duration — the same choice OTel spans make internally (a span record carries `start_time` + `end_time`, not a start event and end event as two log lines). Concretely: `gate_evaluated.payload.duration_ms`, `memory_retrieved.payload.duration_ms`, `context_dropped.payload.duration_ms` (if trimming happened), and `llm_calls.latency_ms` (already in the schema per architecture doc). Total turn latency = `sum(step durations)`, which the internal view can render as a stacked bar — this is a live query (see #4), not worth precomputing at Quorum's scale (single-digit turns/sec at most on a take-home).

No source directly addresses "where the time actually goes" for a bespoke agent pipeline like Quorum's — this is a design inference from OTel span/attribute mechanics (#2) applied to the turn diagram already committed in `docs/ARCHITECTURE.md`, not an externally-validated claim.

**4. Token and cost accounting: precompute vs. live.** Cost tracking guidance converges on "compute at call time, aggregate live" rather than precomputing rollups: cost is derivable per request from token counts and per-model unit prices, so it should be measured in real time and *attributed* via tags (user, session/chat, feature) rather than stored as pre-aggregated totals that go stale ([Braintrust, "How to track LLM costs (2026)"](https://www.braintrust.dev/articles/how-to-track-llm-costs-2026); [Langfuse, "LLM cost management"](https://langfuse.com/resources/engineering/llm-cost-management) — both vendor content, corroborating rather than authoritative on their own, see caveat below). Applied to Quorum: `llm_calls.cost_estimate` is already computed per-call at write time (per `config/models.ts` comment, "Written to `llm_calls.cost_estimate` on every call"). Per-turn and per-chat totals should be `SUM(cost_estimate) WHERE turn_id = / chat_id =` — a live query, not a maintained column, because Quorum has no volume that would make a materialized rollup pay for itself and a stale cached total is worse than a slightly slower live sum. If a global "total spend" figure is ever needed on a dashboard hit far more often than raw event queries, that's the one candidate for a nightly materialized view — not before.

**Caveat on sourcing:** both cost-tracking sources here are vendor blog content (Braintrust, Langfuse — both LLM-observability vendors with a product to sell). Per the research instructions, this is acceptable for orientation but not load-bearing alone; the underlying claim ("cost is computable per-call from token counts × unit price, so track it that way rather than reconciling an invoice") is close to definitional given Quorum already computes `cost_estimate` per call from `config/models.ts` pricing — it doesn't depend on the vendor sources being authoritative, only on arithmetic.

**5. Structured logging fields.** Convergent guidance (multiple secondary sources, no single canonical spec — this is convention, not a standard) recommends every structured log line carry: ISO-8601 timestamp, severity, service name, a snake_case event name, `trace_id`, and `request_id`, with domain fields added as needed ([Dash0 structured logging guide](https://www.dash0.com/guides/structured-logging-for-modern-applications); Google Cloud's trace/log correlation fields `spanId`/`trace`/`traceSampled` follow the same shape — [Google Cloud Trace docs](https://docs.cloud.google.com/trace/docs/trace-log-integration)). Applied to Quorum's server-side lines (route handlers, `lib/events/log.ts`, `lib/llm/anthropic.ts`): every server log line should carry `turn_id`, `request_id`, `chat_id`, and `user_id` (the actor, from `ScopedAgentContext`) at minimum, plus `event_type`/`purpose` where applicable. This is cheap because `ScopedAgentContext` already resolves `chat_id` and the actor once per turn (per `docs/ARCHITECTURE.md` §1) — a thin logger wrapper that reads those off the context and merges them into every `console.log`/`pino` call is a few lines in `lib/events/log.ts` or a sibling `lib/events/logger.ts`, not a new subsystem.

**6. Legibility for a non-engineer reviewer.** No source addresses this directly — it is a Quorum-specific product requirement, not an industry-standard concern (OTel and the cost-tracking vendors all target engineers/SREs as the audience). The design implication, stated without external citation: the internal view (README, "The agent internal view") must translate `event_type` + `payload` into a sentence, not a table of JSON. Concretely, `lib/events/types.ts`'s discriminated union (already planned per `docs/ARCHITECTURE.md` §4) should carry a `toSummary()`-shaped mapping — e.g. `gate_evaluated {verdict: 'silent', rule: 5}` → "Stayed silent — this is a two-person DM and wasn't addressed." — kept alongside the payload type so a new event type is still "no migration" (per the extensibility charter) but *is* a one-line addition to a rendering map in the same file. This is a recommendation, not a finding — flagged as such because it did not come from a source, it comes from applying the "internal view is deliberately the most prominent feature" README claim to what event data alone cannot do (raw JSON is not legible to a non-engineer).

**7. Should `agent_events` be the trace, or derived from it?** Given #1–#3: `agent_events` plus `llm_calls` *together*, joined on `turn_id`, already constitute the trace — no separate "traces" table is needed. `agent_events` is the point-event/log layer; `llm_calls` (and a new lightweight `tool_calls` table, or tool events treated as paired `agent_events` rows sharing a `tool_call_id` in their payload) are the span layer with real durations. This matches the "no OTel dependency" constraint: a trace here is just "all rows across two tables sharing a `turn_id`, ordered by `created_at`," which is exactly the join the internal view (`api/chats/[chatId]/events/route.ts`, per `docs/ARCHITECTURE.md` §4) already needs to do regardless of tracing vocabulary.

## Application to Quorum

- `supabase/migrations/0005_agent_events.sql` (per `docs/ARCHITECTURE.md` §4 migration list, not yet written): add `request_id uuid not null` to both `agent_events` and `llm_calls`, distinct from the existing `turn_id`. This is additive to the schema already sketched, not a redesign.
- Add a `tool_calls` table (or reuse `agent_events` with a `tool_call_id` field inside `payload` for `tool_invoked`/`tool_result` pairs) so tool spans get their own duration without a new migration for every tool — consistent with the "adding a tool costs one file" seam in the extensibility charter (`docs/ARCHITECTURE.md` §5, `lib/agent/tools/*` row).
- `agent_events.payload` gains a `duration_ms` field convention for step-boundary events (`gate_evaluated`, `memory_retrieved`, `context_dropped`) — no migration, per the jsonb seam already documented.
- `lib/events/log.ts` (planned, t1) should accept `{turn_id, request_id, chat_id, actor_id}` once, threaded from `ScopedAgentContext`, rather than have every call site pass IDs individually — reduces the chance a future event type is written without correlation IDs.
- `lib/events/types.ts` (planned, t1): alongside the discriminated payload union, add a co-located human-summary map per event type, feeding the internal view (`api/chats/[chatId]/events/route.ts`, t2) — this is the concrete answer to sub-question 6.
- No new `traces` table, no OTel SDK dependency: per finding 7, `agent_events ⋈ llm_calls ⋈ tool_calls` on `turn_id` **is** the trace.
- `config/agent.ts` gains no new magic numbers from this track; cost/latency thresholds already live there per the CLAUDE.md non-negotiable.
- Recommend opening **D-019** in `docs/DECISIONS.md` recording the `request_id`/`turn_id`/`llm_call_id`/`tool_call_id` hierarchy and the "no separate traces table" call, since this report closes design ambiguity that the current schema sketch left implicit (the architecture doc says `turn_id` threads through both tables and points to R10, but does not yet state the request_id/tool_call_id split or the derived-trace decision).

## Recommendation

This report does not close an existing `OPEN` decision in `docs/DECISIONS.md` — R10 was scoped to strengthen the `agent_events` design, not resolve one of D-004/D-007/D-009/D-011. It proposes a **new** decision, D-019: adopt OTel's span/attribute/event vocabulary as a *design reference only* (no dependency), add `request_id` distinct from `turn_id`, treat `llm_calls` + a new lightweight `tool_calls` table as the span layer and `agent_events` as the point-event layer, and derive "the trace" as a join rather than a stored table.

**Strongest argument against this recommendation:** it adds a table (`tool_calls`) and a column (`request_id`) to a schema that was deliberately kept minimal for a 12-hour build, and the `request_id`/`turn_id` distinction only earns its cost once retries/idempotency (D-011, R8) actually exist — before that lands, `request_id` is a column nothing reads. A leaner counter-argument is: reuse `agent_events` for tool calls too (as `tool_invoked`/`tool_result` events with a shared `tool_call_id` in `payload`, no new table), and skip `request_id` entirely until D-011 is settled, adding it in an additive migration at that point rather than speculatively now. That is very plausibly the *actually correct* call for the remaining time budget — this report recommends the fuller version because it is what "distributed tracing in miniature" without the dependency would look like if fully done, not because the minimal version is wrong for a take-home.

**What would settle it:** whichever way D-011 (idempotency) resolves determines whether `request_id` is load-bearing (if retries can produce a duplicate request against the same `turn_id`, it's needed to distinguish "same turn, second delivery attempt" in the trace) or genuinely unnecessary (if the idempotency key is applied before a `turn_id` even exists, `turn_id` alone may already be a sufficient de-dup key and `request_id` is redundant). Read R8's report before implementing this one's `request_id` recommendation.
