# R3 — Embeddings and vector retrieval

**Band:** A · **Closes:** D-004 · **Status:** complete

## Question

The retrieval design in `docs/ARCHITECTURE.md` names a `memory_items.embedding vector` column and an `ivfflat` index, but **Anthropic ships no embeddings API**, so no provider was ever chosen. This blocks `lib/memory/embed.ts` and the ranking half of `lib/memory/retrieve.ts`. Left open, it also silently blocks the schema, since the column type, dimensionality, and index choice all depend on the answer. The question is not "which embedding model is best" (out of scope per `RESEARCH.md`) — it is: given a ~12-hour build, a free-tier budget, and an authorisation filter that already does the hard work, is a vector provider worth adding at all, and if so, which one, at what index, and behind what interface.

## Findings

### 1. Realistic providers for a 12-hour build, free-tier budget

Anthropic's own documentation is explicit that it has no embeddings offering and directs integrators to Voyage AI as its recommended partner: *"Anthropic does not offer its own embedding model... [Voyage AI is] the rest of this guide"* (platform.claude.com/docs/en/build-with-claude/embeddings). Current Voyage pricing (docs.voyageai.com/docs/pricing): `voyage-4-lite` and the legacy `voyage-3.5-lite` are $0.02/M tokens; `voyage-4` and `voyage-3.5` are $0.06/M tokens; **the first 200M tokens on the voyage-4 family are free**, batch requests get a further 33% discount, but the free-token grant explicitly does *not* apply to the older 3.5 line. Dimensionality is 1024 by default with Matryoshka truncation to 256/512/2048; context length 32K tokens.

The obvious alternative is OpenAI `text-embedding-3-small`: $0.02/M tokens, default 1536 dimensions truncable to 256 via the `dimensions` param (also Matryoshka), 500 RPM / 1M TPM at Tier 1 (developers.openai.com/api/docs/models/text-embedding-3-small; openai.com/index/new-embedding-models-and-api-updates). It requires its own API key and its own account/billing setup — a second vendor, second key, second env var, on top of the Anthropic key this project is already built around.

**Cost is not the deciding factor for either provider at this scale** — a take-home with a handful of test users and a few hundred memory items is nowhere near either free tier's ceiling. The deciding factor is **the number of keys and vendors added under a 12-hour clock**: signing up for a second provider, provisioning a key, adding it to `config/env.ts`'s `serverSchema`, and writing+testing `lib/memory/embed.ts` is real time that competes with tier-1/tier-2 work, for a ranking signal whose value is itself unclear at this row count (see #3).

### 2. Local/in-process models on serverless — not viable here

Transformers.js (ONNX Runtime in WASM) is the realistic "no vendor key" option. Its own field guidance states a quantized MiniLM-class model is ~23MB, but download+deserialize+warm-up cold-start latency alone runs **8–12 seconds on a throttled connection** before the first inference (sitepoint.com, corroborated by Vercel's own bundle-size guidance). Vercel's serverless functions cap at 250MB uncompressed by default (up to 5GB only under Fluid Compute), and Vercel's own docs and community threads confirm **cold-start time correlates directly with bundle size and dependency weight** (vercel.com/kb/guide/troubleshooting-function-250mb-limit). There is a further concrete failure mode: `@huggingface/transformers`'s runtime auto-detection can pick native bindings meant for a persistent server rather than WASM when it runs inside a Node.js Vercel function, which has caused deployment crashes for other teams.

None of this is fatal in principle (Vercel Edge/Fluid Compute plus a genuinely tiny quantized model could work), but it is real infrastructure risk to take on for a ranking signal, inside a 12-hour budget, with no time to debug a cold-start or packaging failure the night before a demo. **Verdict: not worth the risk for v1.**

### 3. The honest fallback — Postgres FTS + recency, no vectors

PostgreSQL's own documentation on `ts_rank`/`ts_rank_cd` states plainly: *"the concept of relevancy is vague and very application-specific"* and ranking is **lexeme-frequency and proximity based — it has no notion of synonyms or semantic relationship** (postgresql.org/docs/current/textsearch-controls.html). That is a real limitation relative to embeddings: `tsvector` will not connect "counsel" and "legal representative," where a semantic embedding would.

But this has to be weighed against what Quorum's own filter step already does. Per `docs/ARCHITECTURE.md` §3 and `config/agent.ts`'s `MEMORY.retrieval.globalItemCap: 24`, the SQL authorisation filter (audience containment + clearance floor) runs *first*, and the assumption throughout the README and architecture doc is that this narrows the candidate set to **tens of items per chat**, not thousands. Industry material on hybrid search is unanimous that vector search earns its keep on *large, high-recall retrieval problems* — one hybrid-search writeup measured pure-vector retrieval at ~62% precision against ~84% for full-text-plus-vector fusion on a large corpus (dev.to/lpossamai). That is a result about ranking *inside a large candidate pool*. Quorum's authorisation step has already done the expensive part of that job — cutting an unbounded memory table down to a small authorised set — before ranking ever runs. Over tens of items, `ts_rank` plus the existing recency/speaker-presence weights in `MEMORY.retrieval.weights` is very unlikely to be measurably worse than embeddings, and no source found in this research measures embedding-vs-FTS quality specifically at candidate-set sizes this small — **this is the one place the evidence does not settle the question outright; see Recommendation.**

### 4. `ivfflat` vs `hnsw` — and neither may matter at this scale

Supabase's own vector-index documentation states unambiguously: *"HNSW should be your default choice when creating a vector index"* and, unlike IVFFlat, *"you are safe to build an HNSW index immediately after the table is created"* — IVFFlat's list-based clustering is computed at build time via k-means, so an index built on a near-empty table is poorly tuned until the table grows (supabase.com/docs/guides/ai/vector-indexes/hnsw-indexes). The pgvector project's own README states IVFFlat recommends `lists = rows / 1000` for tables under ~1M rows (github.com/pgvector/pgvector) — with, say, 500 memory rows that formula rounds to `lists = 1` (or 0), which is a degenerate index. HNSW has no equivalent training-data dependency but costs more to build and more memory per the same source.

More basically: pgvector's own documentation is explicit that **"if the table is small, a table scan may be faster"** than using either index at all (github.com/pgvector/pgvector, README indexing section). At the row counts a 12-hour build will plausibly produce — dozens to low hundreds of memory rows per deployment — a sequential scan over an already-tiny table is very likely faster and simpler than maintaining either ANN index, and completely avoids the recall degradation described in #5.

### 5. Filtering before ranking, combined with an ANN index — this is where it gets structurally interesting for Quorum

This is the sub-question with the most concrete, quantified answer, and it matters because it is not hypothetical for this codebase — `docs/ARCHITECTURE.md` states the retrieval order is explicitly **filter (SQL) → rank (TypeScript) → cap**, and CLAUDE.md non-negotiable #4 states *"filter before rank, always."*

A pgvector-focused writeup with a reproducible demo shows exactly what goes wrong when a `WHERE` filter and an ANN index (`ivfflat`/`hnsw`) are combined in the *same query*: **the ANN index is scanned first and the filter is applied to whatever it returns, not the other way around.** In a 2M-row demo, an exact scan returned 15 true nearest neighbours matching a colour filter down to similarity 0.206; the same query through an HNSW index with the default `ef_search=40` returned only 11, because the index spent most of its 40 candidate slots on rows that the filter then discarded (dev.to/franckpachot, corroborating pgvector's own documented `iterative_scan` feature, which exists specifically to correct for this by re-scanning until enough post-filter rows are found — github.com/pgvector/pgvector). **A naive "put a WHERE clause on the audience/clearance filter and ORDER BY the embedding distance operator" query would silently under-return authorised, on-topic memories** — the wrong failure direction for a system whose entire thesis is "don't leak," but a real usability defect (relevant memories going missing) if that pattern were used here.

This is exactly the situation the architecture doc's split already avoids: because `lib/memory/retrieve.ts` is specified as *filter is SQL; rank is TypeScript over the already-authorised set*, Quorum's design **never asks Postgres to combine a `WHERE` clause with an ANN `ORDER BY <=>` in one query in the first place.** The authorisation filter runs as a plain (non-vector) SQL query, returns the small authorised set, and if a semantic score is computed at all, it is computed in application code over those already-fetched rows' embeddings — sidestepping the ANN-plus-filter recall problem entirely, at the cost of doing the distance math in TypeScript instead of the database. At the row counts in #4 (tens of authorised candidates), computing cosine similarity in TypeScript over an array of already-fetched float vectors is cheap and requires no ANN index at all.

### 6. Dimensionality and storage

pgvector stores `vector` as `4 * dimensions + 8` bytes; `halfvec` (half-precision) as `2 * dimensions + 8` bytes, supporting up to 16,000 dimensions with indexing possible up to 4,000 (github.com/pgvector/pgvector). At 1024 dimensions (Voyage/OpenAI default), a `vector` column costs ~4.1KB/row — trivial at hundreds-to-low-thousands of rows; the smaller Matryoshka-truncated 256-dim option (both Voyage and OpenAI support this) would cost ~1KB/row with graceful quality degradation per both providers' documentation, and is a reasonable choice if vectors are adopted at all, since it also shrinks whatever in-app cosine-similarity computation is done per #5.

**Normalise before storing.** Voyage's own FAQ states its embeddings are already normalised to unit length, making cosine similarity and dot-product equivalent — dot product is cheaper (platform.claude.com/docs/en/build-with-claude/embeddings, FAQ section). pgvector's documentation confirms cosine distance is `1 - cosine similarity` and that normalised vectors make cosine and inner-product operators produce identical rankings (github.com/pgvector/pgvector). If Voyage is the provider, no extra normalisation step is needed; if a different provider is substituted later, normalisation should happen at write time, not query time.

### 7. What breaks when the provider changes later

This is a real, documented operational hazard, not a theoretical one. A vector produced by model A is not comparable to one produced by model B — mixing them in one similarity search silently produces meaningless rankings, not an error. Qdrant's own migration documentation frames this as a full re-embed-and-reindex operation; a HackerNoon writeup on embedding-model deprecation and a Medium zero-downtime writeup both describe the standard mitigation as a **dual-column (old-embedding + new-embedding) schema with a background backfill job, cut over only once the new column is fully populated**, rather than an in-place migration (qdrant.tech/documentation/tutorials-operations/embedding-model-migration; hackernoon.com/your-embedding-model-will-deprecate-heres-what-to-do). One cited real incident: an organisation's embedding model was deprecated by its vendor overnight, breaking every retrieval query in production until they completed an emergency 48-hour dual-column migration.

This is a strong argument *for* keeping the embedding step behind an interface (already the plan — `lib/memory/embed.ts`) and *against* baking a provider-specific dimensionality assumption into the `memory_items` schema without an explicit `embedding_model` column to make a future migration detectable rather than silent.

## Application to Quorum

**Recommended shape for `config/`, the schema, and `lib/memory/`:**

- **`lib/memory/embed.ts`** — ship as a typed interface (`embed(text: string, kind: 'query'|'document'): Promise<number[] | null>`) with **no implementation wired into the retrieval path for v1**. `retrieve.ts`'s rank step falls back to the FTS+recency+speaker-presence formula already specified in `config/agent.ts` (`MEMORY.retrieval.weights`) when no embedding is available. This matches the existing weight split (`similarity: 0.6, recency: 0.2, speakerPresence: 0.2`) — "similarity" can be sourced from `ts_rank` against a generated `tsvector` column instead of cosine distance, with the same weight, until/unless embeddings are added.
- **`supabase/migrations/0006_memory.sql`** — do **not** add `USING ivfflat (embedding vector_cosine_ops)` as currently sketched in `docs/ARCHITECTURE.md` §2's index list. Add a generated `tsvector` column (`content_tsv`) with a GIN index instead for v1; keep the `embedding vector(1024)` column nullable and *unindexed* so the schema is forward-compatible without committing to an index choice that's wrong at this row count (finding #4). If vectors are added later, add the HNSW index in a separate additive migration once real row counts are known — HNSW, not ivfflat, per finding #4, since it needs no k-means training step and Supabase's own docs recommend it as the default.
- **`memory_items`** — add an `embedding_model text nullable` column alongside `embedding`. This makes finding #7 detectable rather than silent: a null or mismatched `embedding_model` value tells `retrieve.ts` to skip the vector similarity term for that row rather than comparing incomparable vectors.
- **`lib/memory/retrieve.ts`** — per finding #5, if/when vector ranking is added, it must **not** be implemented as a single SQL query that combines the audience/clearance `WHERE` filter with `ORDER BY embedding <=> query_embedding`. The existing architecture-doc plan — filter in SQL, fetch the small authorised set, rank in TypeScript — is the correct shape and should stay exactly as specified; this research confirms *why* it is correct (it structurally avoids the ANN-post-filter recall bug) rather than being merely a convenient split.
- **`config/env.ts`** — the `EMBEDDING_API_KEY` field already exists as optional in `serverSchema`; no change needed there, but do not add a required Voyage key for v1 given the fallback above.
- **`docs/ARCHITECTURE.md`** — the "Indexes on the hot paths" table (line ~95) should be corrected: replace the ivfflat line with `memory_items USING GIN (content_tsv)` for v1, with a footnote pointing at this report for the deferred HNSW addition.

## Recommendation

**Closes D-004.** Recommended option: **Option 3 from the DECISIONS.md leaning — Postgres full-text search + the existing recency/speaker-presence weights as the v1 ranker, no vector provider wired into the retrieval path, with `lib/memory/embed.ts` shipped as an unimplemented interface** so Voyage AI (the option-1 pick, since it is Anthropic's own documented recommendation and its 200M-token free tier trivially covers this project's scale) can be added later as a pure ranking-signal upgrade without touching the filter or the schema's authorisation logic.

**The strongest argument against this recommendation:** Postgres FTS has a real, documented capability gap — it matches lexemes, not meaning (finding #3) — and this project is explicitly pitched as a *legal* product, where the vocabulary mismatch between how a fact was phrased when learned and how it is needed later ("Delaware governing law" vs "the client's choice-of-law clause") is exactly the kind of gap semantic embeddings are built to close. If a demo scenario specifically needs to show a memory surfacing under paraphrase rather than exact term match, the FTS fallback will visibly fail that demo, and there is no evidence in this research (positive or negative) measuring FTS-vs-embedding quality specifically at the small candidate-set sizes (tens of items) that Quorum's authorisation filter produces — every comparison found here was measured at large-corpus scale, where vectors' advantage is well established. That gap is real and unresolved by this research.

**What would settle it:** running Quorum's own planned demo memory fixtures (a handful of paraphrased facts) through both `ts_rank` and a cheap embedding call (Voyage's free tier costs nothing to test) and comparing which one actually surfaces the right memory in the top-24-item cap. That is a ~30-minute experiment against real fixture data rather than literature, and it is the only way to close the gap this report leaves open. If time allows in tier 2, run it before finalising the ranker; if not, the FTS fallback is the defensible default to ship, documented in the README as a stated, reasoned tradeoff rather than an oversight — matching how D-004's leaning was already written before this research began.
